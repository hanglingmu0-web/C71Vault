# Optical protocol v2: binary data, four colors, batch acknowledgments

Added in C71 Vault 0.3.0. The original `C71O1` / `C71A1` protocol remains
available unchanged. Select the same mode on both devices; there is no silent
fallback between protocols.

## Transfer model

- PC → Android: encrypted archives only, in signed binary packets.
- Android → PC: signed, bounded acknowledgments and status codes only.
- Maximum archive: 16 MiB. Maximum data per displayed frame: 1,024 bytes.
- Window size: at most eight data frames. Only missing frames are retransmitted.
- Initial pairing, recovery key custody, archive export, and key retrieval use USB.
- Success requires archive storage, readback verification, and a verified final ACK.

The optical code is specific to this project. It is not HCC2D or JAB Code.
Four colors encode two superimposed byte-mode QR planes. White represents
two light cells, black two dark cells, cyan a dark red-channel plane, and
red a dark blue-channel plane. Both planes share their QR version, error
correction level M, and mask. Small control packets use smaller QR versions;
data packets require at most version 20. A four-module white margin is retained
around the complete symbol. Rendering uses integer scaling.

Android processes the red and blue channels from NV21 camera frames. If one
plane's QR finder cannot be read, it can use the other plane's detected geometry
to sample its own grid. Each plane still has to pass QR decoding, followed by
the shared packet hash and signature checks. This is not a general solution to
glare or color distortion; both planes must be readable.

## Binary packet

All integers use big-endian encoding. No Base64 or JSON wraps the forward
packet. Each packet is signed with the registered PC's existing ECDSA P-256 key.

| Field | Bytes |
|---|---:|
| Magic `C7D2` | 4 |
| Operation: BEGIN=0, DATA=1, POLL=2, END=3 | 1 |
| Session ID generated by Android | 16 |
| Transfer ID generated by Windows | 16 |
| PC public key SHA-256 identifier | 32 |
| Sequence number | 4 |
| Body length | 2 |
| Body | 0–1,024 |
| DER signature length | 1 |
| ECDSA-SHA256 signature over header and body | Up to 72 |

The maximum complete packet is 1,172 bytes. A 1,024-byte data packet therefore
requires at most 148 additional bytes for authentication and framing.

BEGIN has sequence 0. Its body contains archive length (8), SHA-256 (32), ASCII
recovery key ID (16), source ID (16), UTF-8 label length (2), and label bytes.
The label is limited to 100 UTF-16 code units with no control characters.

DATA sequences start at 1. Every data body is 1,024 bytes except the final
chunk, whose exact length follows from the declared archive length.

POLL uses the first sequence number of the current window. Its body is a fresh,
nonzero 32-bit token. The token is echoed in the signed ACK, preventing a stale
partial ACK from being accepted as the answer to a later poll.

END has sequence `data_chunk_count + 1` and an empty body.

## Color plane framing

Split the complete signed packet in half, rounding the first half up. Each
plane contains one QR byte segment with the following header and its half:

| Field | Bytes |
|---|---:|
| Magic `C7L2` | 4 |
| Plane index: 0 or 1 | 1 |
| Complete packet length | 2 |
| First 16 bytes of complete packet SHA-256 | 16 |
| Packet half | Variable |

Both halves must come from the same captured image, identify the same packet,
have the expected lengths, and pass the combined hash check. The packet's PC
signature is then verified before any data is accepted. The truncated hash is
for detecting mixed planes; it does not replace authentication.

## Batch ACK

ACKs remain monochrome QR text:

```text
C71A2:<Base64 of binary status>.<Base64 of DER ECDSA signature>
```

The device signature covers the status bytes exactly. The normal status is
51 bytes; a final stored status is 83 bytes. Other lengths are rejected.

| Field | Bytes |
|---|---:|
| Version, fixed to 2 | 1 |
| Session ID | 16 |
| Transfer ID, zero before BEGIN | 16 |
| Window base or control sequence | 4 |
| POLL token, zero for BEGIN/END/ready | 4 |
| Received bitmap, bit 0 corresponding to the window base | 1 |
| Status code | 1 |
| Received byte count | 8 |
| Archive SHA-256, only for stored status | 32 |

Status codes are inherited from v1: ready, ack, stored, sequence, unregistered,
key_missing, capacity, exists, invalid, forbidden, and hash_mismatch. There is
no field for arbitrary device text or file content.

## Receiver state and persistence

The receiver accepts out-of-order chunks within the current eight-frame window
and buffers at most 8 KiB. An exact duplicate is harmless. Conflicting contents
for a sequence, chunks outside the current window, mismatched sessions or
transfers, and invalid signatures cannot advance the transfer.

The sender displays data frames without waiting for an individual ACK. It then
holds a POLL frame until the matching signed response arrives. A partial bitmap
causes only the missing data frames to be displayed again, followed by a fresh
POLL token. Ordinary data frames do not trigger an ACK redraw.

A full window is appended to the temporary archive and synced before its full
ACK is issued. A partial ACK describes verified in-memory chunks; it is not a
durability or completion receipt. The previous window's hashes are retained
for bounded duplicate checking. A failed write closes the session rather than
retrying an uncertain append.

END is accepted only after all windows are complete. The receiver checks the
complete archive hash, passes it through the existing vault storage and readback
verification path, and signs the final stored status. Repeating END returns the
same completion receipt. If that final receipt is lost, use USB history to check
whether the archive was committed.

Closing the receiver removes that session's temporary archive. This version
does not resume an interrupted session after app restart. Camera images are
processed in memory and are not saved by the app.

## Timing and validation

The default data-frame display interval is 1 second, configurable from 0.2 to
3 seconds. The interval starts after the GUI has rendered the frame. Encoding,
camera exposure, decoding, polls, and retries add time; the interval alone does
not establish throughput. Use sufficient lighting, avoid reflections, and keep
the complete code and its white margin in view.

Automated coverage includes binary signatures, arbitrary byte values, mixed
plane rejection, image brightness/color/blur/perspective transforms, Android
NV21 chroma subsampling, out-of-order windows, selective retransmission, stale
session rejection, key custody/quota checks, and commit only after END. See
[VALIDATION.md](VALIDATION.md) for the exact hardware test scope.
